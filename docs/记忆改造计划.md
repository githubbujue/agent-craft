## 一、现状全景（代码核实，非推测）

### 1.1 两条轨并存

```
用户提问
  │
  ├─【Java 轨】事实存档，跨会话永久
  │    ChatServiceImpl / ChatStreamServiceImpl
  │      → conversationContextService.getConversationContext(id, 10)   ← 从 MySQL 取最近 10 条
  │      → 拼成 "user: xxx\nassistant: yyy"
  │      → AiServiceImpl:311  requestBody.put("context", ...)
  │
  │    消息落库时（ChatPersistenceServiceImpl:41/59 → updateConversationContext）
  │      → 滑动窗口 + Caffeine/Redis 缓存（key=conv:ctx:{id}，TTL 1800s）
  │      → 每 5 条：generateConversationSummary()   【关键词提取，不调 LLM】
  │      → 每 10 条：saveLongTermMemory()           【真写 conversation_context 表】
  │
  └─【Python 轨】模型上下文，24 小时
       knowledge_qa_agent.ask()
         → conversation_memory_read(limit=10)        ← 从 Redis 取最近 10 条
         → _format_history()  拼成 "用户: xxx\nAI: yyy"
         → full_context = f"{context}\n\n{conversation_history}"   ← ★ 与 Java 轨叠加
         → _ask_l1 / _ask_l2
         → conversation_memory_write() 写回
```

### 1.3 关键结论：重复从第一天就存在，修好透传后才显形

```
61ebd6d（初始提交）
  ├─ Java 已把 getConversationContext(10) 拼进 context
  └─ Python 已写 full_context = context + conversation_history
      → 双轨从第一天成立

踩坑笔记 §2「会话记忆链断裂」

  → Python 读不到 Redis → conversation_history = ""
```

**这不是"修坏了"**，而是修复让一个从未被定义的问题暴露出来：**从来没有人规定"上下文由谁负责"**。
当时的验证方式（看 Python 日志 `Loaded N messages`）只覆盖了一路，看不出另一路也在塞。

## 三、改造原则

1. **单一职责**：Java 管"事实存档"（审计、管理端展示），Python 管"喂模型的上下文"。两边的数据可以重叠，**但拼进同一个 prompt 的内容不能重叠**。
2. **先减法后加法**：P0 是纯减法，改完立刻能测出效果；P1 之后都是给模型加信息，加错了会降低回答质量。
3. **每阶段可独立上线、可独立回滚**。
4. **不引入新中间件**：复用现有 MySQL + Redis；只有 P2 需要向量检索时才考虑 Milvus。

## 四、阶段 1（P0）：消除重复注入 ✅ 已完成（2026-11-14）

**目标**：一次 prompt 里，历史对话只出现一次。

**实施结果**：改动 5 个文件，实测 prompt 上下文长度从约 4 万字符降到 9307 字符（降幅约 77%），
且摘要是压缩表示、不与最近几轮原文重复。

### 4.1 最终方案：Java 只传摘要，Python 传最近 5 条原文

| 侧 | 传什么 | 为什么 |
|---|---|---|
| Java | `conversation_context.summary`（存在时，前缀"【更早的对话摘要】"）；不存在则传空串 | 摘要覆盖更早的历史，MySQL 永久不过期 |
| Python | 最近 5 条原文 | 保证衔接自然，且保留 LLM 压缩能力 |

> **与原方案的差异（实施时调整）**：原计划是"摘要 + 最近 2 条原文"，实施时改为**只传摘要**。
> 原因：那 2 条原文必然包含在 Python 读取的最近 5 条里，仍会重复。改成"摘要 + 5 条原文"后，
> 两者形态不同（压缩表示 vs 原文），边界清晰。

**为什么不选其他方案**：

| 方案 | 否决理由 |
|---|---|
| 删掉 Java 的 context | Redis 24h 过期后历史全丢，长对话断裂 |
| 删掉 Python 的 Redis 读取 | 失去 LLM 压缩能力，Java 的摘要是关键词提取，质量差 |
| 两边都保留但只取较短的一边 | 逻辑上等价于选一个，不如显式分工 |

### 4.2 实际改动（已完成，共 5 个文件）

## 五、阶段 2（P1）：让 `user_memory` 真正可用（Step 1-2 ✅ 已完成 2026-11-14）

### 5.1 Step 1：建表 ✅

已加入 `sql/init.sql` 末尾，用 `CREATE TABLE IF NOT EXISTS` 而非 `DROP + CREATE`，
避免重新导入脚本时清空已积累的记忆数据（其余表保持 dump 原样）：

```sql
CREATE TABLE IF NOT EXISTS `user_memory` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `user_id` varchar(64) NOT NULL COMMENT '用户ID',
  `memory_key` varchar(64) NOT NULL COMMENT '记忆键, 如 preference.answer_style',
  `memory_value` text COMMENT '记忆值(JSON)',
  `source` varchar(32) DEFAULT 'agent' COMMENT '来源: explicit/inferred/agent',
  `confidence` double DEFAULT '1.0' COMMENT '置信度 0-1',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_key` (`user_id`, `memory_key`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户长期记忆';
```

`UserMemoryClient` 的 SQL 已经是 `ON DUPLICATE KEY UPDATE` 写法，与这个唯一键完全对应，建表后立即可用。
本地已执行并确认 8 个字段：`id / user_id / memory_key / memory_value / source / confidence / create_time / update_time`。

### 5.2 Step 2：只读接入 ✅

`knowledge_qa_agent.ask()` 在读完会话记忆之后、合并上下文之前读取：

```python
# 1.5 读取用户长期偏好（MySQL user_memory，缺失或异常时静默跳过）
user_memory_text = ""
if user_id:
    try:
        from core.mysql_client import user_memory_client
        memories = user_memory_client.get_user_memory(str(user_id)) or {}
        if memories:
            items = list(memories.items())[:10]      # 最多 10 条
            user_memory_text = json.dumps(dict(items), ensure_ascii=False)
            if len(user_memory_text) > 500:          # 最多 500 字符
                user_memory_text = user_memory_text[:500] + "..."
    except Exception as e:
        logger.warning(f"[KnowledgeQAAgent] Failed to load user memory: {e}")

if user_memory_text:
    block = f"[用户长期偏好] {user_memory_text}"
    full_context = f"{full_context}\n\n{block}" if full_context else block
```

两处防御是刻意加的：

- **条数与字符上限**：记忆条目不受控时会把 Prompt 撑爆
- **延迟 import + try/except**：MySQL 不可用时不能影响问答主流程

**这一步不改写入**，即使读到脏数据也只影响本次回答，可随时下线。

### 5.3 Step 3：写入接入（分两种来源）

| 来源 | 触发 | confidence | 风险 |
|---|---|---|---|
| **显式** | 用户说"记住我喜欢简洁的回答" | 1.0 | 低，但需要意图识别支持 |
| **推断** | 从对话里抽偏好 | 0.6-0.9（LLM 打分） | 高，会污染记忆 |

**第一版建议只做显式 + 极简规则推断**（例如"我是做 Java 的"→ `occupation=Java`），
不做开放式 LLM 抽取。理由：抽取幻觉一旦写库，无法区分"用户真说过"和"模型编的"，
而且没有纠错入口时，错误记忆会长期生效，**比没有记忆更糟**。

如果要做，必须同时提供：
- 记忆查看/删除接口（至少管理端有）
- `source` 与 `confidence` 落库，低置信度不参与 prompt
- 抽取失败静默，不阻断主链路

## 六、阶段 2.5（P3 + P4）：摘要架构收敛（rolling summary）

> 业界标准做法是 **rolling summary（滚动摘要）**：早期历史压成摘要、最近 N 轮保留原文、两者拼进 Prompt。
> 本项目「摘要 + 最近 5 条原文」的分工已经对了（阶段 1），但这套摘要本身的**生成与存储完全不符合标准**。

### 6.1 四条硬标准 vs 现状

| # | 标准 | 当前 | 判定 |
|---|---|---|---|
| 1 | **事实源唯一**：持久化存摘要，Redis 只做缓存 | MySQL 一份（关键词桩）+ Redis 一份（LLM，TTL 1h），互不相通 | ❌ |
| 2 | **生成器唯一**：同一 prompt、同一模型 | Java 关键词提取（58% 输出空壳）+ Python LLM | ❌ |
| 3 | **可增量**：记录摘要覆盖到哪条消息 | 无游标，每次都要全量扫消息表 | ❌ |
| 4 | **异步 + 可抑制**：不阻塞写消息、不重复触发 | 同步执行在 `@Transactional` 内 | ❌ |

现状证据：

```
摘要长度分布（24 条）
  0 字符 1 条 | 7 字符 9 条 | 9 字符 4 条      ← 58% 是空壳
  37~56 字符 5 条 | 139~264 字符 4 条
  1089 / 1265 字符 各 1 条                     ← 另一个极端：整句噪声
```

同步阻塞证据：

```126:127:src/main/java/com/demo/aiknowledge/service/impl/ConversationContextServiceImpl.java
    @Transactional
    public void updateConversationContext(Long conversationId, Long userId, Message newMessage) {
```

方法内部 `shouldGenerateSummary()`（全量查消息）+ `generateConversationSummary()`（全量查消息 + 写库）都在
这个事务里，而它由 `ChatPersistenceServiceImpl.saveUserMessage()`（同样是 `@Transactional`）调用 ——
每来一条消息全量扫一次 `message` 表，每 5 条再扫一次并写库，事务与行锁时间被拉长。

### 6.2 目标架构

```
写入路径
  消息落库（事务已提交）
     │ 触发条件：新增消息数 >= 5  或  估算 token > 2000
     ▼
  CAS 抢占：UPDATE conversation_context
            SET summary_status = 'generating'
            WHERE conversation_id = ? AND summary_status <> 'generating'
     │ 影响行数 = 1 才继续（并发抑制：同一会话同时只跑一个任务）
     ▼
  taskExecutor.execute()   ← 复用现有 TaskExecutor，不阻塞请求
     │ 取 id > summary_msg_id 的消息（增量，不全量）
     ▼
  POST /api/internal/summarize    ← Java 调 Python（RestTemplate，与 AiServiceImpl 同套路）
     │ Header: X-Internal-Token；超时 10s
     │ Body: { old_summary, messages[], base_msg_id }
     ▼
  Python: LLM 合并摘要（复用 memory_read._compress_history 的 prompt）
     │
     ├─ 成功 → UPDATE summary / summary_msg_id / version+1 / status='ready'
     │         DEL Redis conv:summary:{id}
     └─ 失败 → status='failed'，**保留旧摘要**（旧摘要可继续用，不影响业务）

读取路径
  buildConversationContext()
     │ 读 Redis conv:summary:{id}（TTL 24h，与消息同寿命）
     │   └─ miss → 查 MySQL summary → 回填 Redis
     ▼
  "【更早的对话摘要】" + Python 侧最近 5 条原文
```

关键点：**Redis 从这里开始只是缓存**。删掉它，系统仍然正确，只是多一次 MySQL 查询。

### 6.3 数据模型变更

```sql
ALTER TABLE `conversation_context`
  ADD COLUMN `summary_msg_id` bigint DEFAULT NULL COMMENT '摘要覆盖到的最后一条消息ID（游标）',
  ADD COLUMN `summary_version` int DEFAULT '0' COMMENT '摘要版本，每次重生成 +1',
  ADD COLUMN `summary_status` varchar(16) DEFAULT 'none' COMMENT 'none/generating/ready/failed',
  ADD COLUMN `summary_update_time` datetime DEFAULT NULL COMMENT '摘要最后生成时间';
```

现有 `summary` 字段保留；`embedding` 留给阶段 3（向量检索），本阶段不动。

**为什么要游标**：没有它，异步只是把「同步阻塞」变成「异步浪费」—— 会话到 100 条时，每次摘要仍要
重读 100 条，其中 95 条上次已经处理过。有 `summary_msg_id` 才能只处理增量。

|---|---|
| prompt | 复用 `tools/memory_read.py:145-153` 那套（问什么 / 答什么要点 / 用户偏好），追加"已有摘要"段落 |
| 输入裁剪 | 单条消息截断到 500 字，总输入上限约 6000 字，超出取最近的 |
| 失败降级 | 返回 5xx，Java 用规则摘要兜底（见 §6.6 第 3 步）|
| 超时 | Java 侧 10s；Python 侧 LLM 超时 8s |

### 6.5 分三步实施（每步可独立上线、独立回滚）

**第 1 步：数据与读取（无行为变化）**
- 执行 §6.3 的 DDL
- Java `buildConversationContext()` 改为「先读 Redis 缓存 → miss 查 MySQL → 回填」
- 验证：摘要来源仍是原来的（可能是空壳），但读取路径已经收敛

**第 2 步：异步生成 + 并发抑制**
- `saveAssistantMessage()` 事务提交后触发异步摘要任务（不在事务内）
- 加 CAS 抢占与 `summary_status` 状态机
- 此时生成器仍用 Java 关键词桩 —— 先验证「不阻塞、不重复、游标正确推进」

**第 3 步：生成器切到 Python LLM**
- 新增 `/api/internal/summarize`（带内部 token + 超时）
- Java 异步任务改调该接口，成功写库；失败保留旧摘要
- **删除 Python `memory_read` 的摘要生成**（`conversation:{id}:summary` 不再写入）
- 关键词桩降级为"LLM 不可用时的兜底"，不再是主路径

### 6.6 验收标准

```
□ 摘要非空率 > 90%（当前 42%）
□ 同一会话连续发 3 条消息，只触发 1 次摘要生成（并发抑制生效）
□ 消息落库接口的耗时与改造前持平（摘要已移出事务）
□ 摘要覆盖的消息游标与 message 表一致（抽查：summary_msg_id 对应的消息内容在摘要范围内）
□ 手动删掉 Redis 的 summary key，读取仍正确（回源 MySQL 生效）
□ 停掉 Python 服务后发消息，问答主流程不受影响，status 记为 failed
□ pytest 54 项全绿
```

### 6.7 风险与回滚

| 风险 | 应对 |
|---|---|
| 摘要任务失败导致摘要长期不更新 | `status='failed'` 可被下次触发覆盖；同时保留旧摘要，不至于"没摘要" |
| 异步线程池被打满 | 摘要任务用独立线程池或低优先级队列，与流式响应隔离 |
| LLM 生成摘要不稳定 | 超时 + 失败降级到规则摘要；规则摘要代码保留不删 |
| 增量摘要丢失上下文 | 每次把 `old_summary` 一并传入，让模型做"合并"而非"重写" |
| 回滚 | 三步各自独立提交；第 3 步出问题可回退到关键词桩，前两步仍然有效 |

**工作量**：第 1 步 0.5 天 / 第 2 步 0.5 天 / 第 3 步 1 天，合计约 2 天。

### 6.8 明确不做的

| 不做 | 原因 |
|---|---|
| 摘要向量化（写 `embedding`） | 属于阶段 3 的跨会话检索，本阶段不做 |
| 多级摘要树（会话级 / 主题级 / 用户级） | 当前会话长度远达不到需要分级摘要的量级 |
| 摘要人工审核界面 | 收益低于成本；`status` 字段已够排查 |
| 摘要存多版本历史 | 只保留最新一版 + 版本号，历史无查询需求 |

## 七、阶段 3（P2）：跨会话检索

`findSimilarConversations()` 要能用，前提是**按 user_id 过滤的向量检索**。

| 方案 | 可行性 | 说明 |
|---|---|---|
| FAISS + 后过滤 | ⚠️ 能跑但低效 | FAISS 不支持元数据过滤，只能全量召回再筛 |
| Milvus + filter | ✅ 推荐 | `USE_MILVUS=true` 后 `vector_store.search(filter_dict=...)` 已支持 |
| MySQL 关键词 + 重要性排序 | ✅ 最简单 | 就是现在的实现，先把功能接上 |

**建议路线**：
1. 先把 `findSimilarConversations` **接进链路**（哪怕仍是关键词匹配），让"跨会话记忆"可用；
2. 补 `conversation_context.embedding` 写入（P4）；
3. 用户量/数据量上来后再切 Milvus 过滤。

**工作量**：接链路 1 天；补 embedding 1 天；切 Milvus 1-2 天。

## 九、明确不做的事

| 不做 | 原因 |
|---|---|
| 引入专门的记忆框架（Mem0 / Zep 等） | 当前规模用 MySQL + Redis 足够，引入后调试成本高于收益 |

## 十、排序与工作量汇总

| 阶段 | 内容 | 工作量 | 风险 | 建议 |
