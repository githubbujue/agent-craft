## 一、现状全景（代码核实，非推测）

### 1.1 两条轨并存

```
用户提问
  │
  ├─【Java 轨】事实存档，跨会话永久
  │    ChatServiceImpl / ChatStreamServiceImpl
  │      → conversationContextService.getConversationContext(id, 10)   ← 从 MySQL 取最近 10 条
  │      → 拼成 "user: xxx\nassistant: yyy"
  │      → AiServiceImpl:311  requestBody.put("context", ...)
  │
  │    消息落库时（ChatPersistenceServiceImpl:41/59 → updateConversationContext）
  │      → 滑动窗口 + Caffeine/Redis 缓存（key=conv:ctx:{id}，TTL 1800s）
  │      → 每 5 条：generateConversationSummary()   【关键词提取，不调 LLM】
  │      → 每 10 条：saveLongTermMemory()           【真写 conversation_context 表】
  │
  └─【Python 轨】模型上下文，24 小时
       knowledge_qa_agent.ask()
         → conversation_memory_read(limit=10)        ← 从 Redis 取最近 10 条
         → _format_history()  拼成 "用户: xxx\nAI: yyy"
         → full_context = f"{context}\n\n{conversation_history}"   ← ★ 与 Java 轨叠加
         → _ask_l1 / _ask_l2
         → conversation_memory_write() 写回
```

### 1.3 关键结论：重复从第一天就存在，修好透传后才显形

```
61ebd6d（初始提交）
  ├─ Java 已把 getConversationContext(10) 拼进 context
  └─ Python 已写 full_context = context + conversation_history
      → 双轨从第一天成立

踩坑笔记 §2「会话记忆链断裂」
  conversation_id 未跨服务透传
  → Java getConversationContext(null) 返回空 → context = ""
  → Python 读不到 Redis → conversation_history = ""
  → 两路都空 → 表现为"AI 失忆"
  修复：Java 请求体加 conversation_id（+ user_id）

修复之后
  → Java 那路有 10 条了
  → Python 那路也有 10 条了
  → ★ 重复第一次显形
```

**这不是"修坏了"**，而是修复让一个从未被定义的问题暴露出来：**从来没有人规定"上下文由谁负责"**。
当时的验证方式（看 Python 日志 `Loaded N messages`）只覆盖了一路，看不出另一路也在塞。

## 三、改造原则

1. **单一职责**：Java 管"事实存档"（审计、管理端展示），Python 管"喂模型的上下文"。两边的数据可以重叠，**但拼进同一个 prompt 的内容不能重叠**。
2. **先减法后加法**：P0 是纯减法，改完立刻能测出效果；P1 之后都是给模型加信息，加错了会降低回答质量。
3. **每阶段可独立上线、可独立回滚**。
4. **不引入新中间件**：复用现有 MySQL + Redis；只有 P2 需要向量检索时才考虑 Milvus。

## 四、阶段 1（P0）：消除重复注入 ✅ 已完成（2026-11-14）

**目标**：一次 prompt 里，历史对话只出现一次。

**实施结果**：改动 5 个文件，实测 prompt 上下文长度从约 4 万字符降到 9307 字符（降幅约 77%），
且摘要是压缩表示、不与最近几轮原文重复。

### 4.1 最终方案：Java 只传摘要，Python 传最近 5 条原文

| 侧 | 传什么 | 为什么 |
|---|---|---|
| Java | `conversation_context.summary`（存在时，前缀"【更早的对话摘要】"）；不存在则传空串 | 摘要覆盖更早的历史，MySQL 永久不过期 |
| Python | 最近 5 条原文 | 保证衔接自然，且保留 LLM 压缩能力 |

> **与原方案的差异（实施时调整）**：原计划是"摘要 + 最近 2 条原文"，实施时改为**只传摘要**。
> 原因：那 2 条原文必然包含在 Python 读取的最近 5 条里，仍会重复。改成"摘要 + 5 条原文"后，
> 两者形态不同（压缩表示 vs 原文），边界清晰。

**为什么不选其他方案**：

| 方案 | 否决理由 |
|---|---|
| 删掉 Java 的 context | Redis 24h 过期后历史全丢，长对话断裂 |
| 删掉 Python 的 Redis 读取 | 失去 LLM 压缩能力，Java 的摘要是关键词提取，质量差 |
| 两边都保留但只取较短的一边 | 逻辑上等价于选一个，不如显式分工 |

### 4.2 实际改动（已完成，共 5 个文件）

**改动 1：新增只读摘要方法**

`ConversationContextService` 接口 + `ConversationContextServiceImpl` 实现各加一个：

```java
String getConversationSummaryIfPresent(Long conversationId);
```

为什么不直接用已有的 `getConversationSummary()`：它在摘要缺失时会**现场重新生成并写库**
（全量扫消息表 + `updateById`），每次提问都调用代价太大。新方法只 `selectOne` 一次，
缺失返回 `null`，异常也返回 `null`——摘要只是上下文补充，不能影响问答主流程。

**改动 2：Java 两处构建上下文改为只传摘要**

`ChatServiceImpl`（同步链路，原 108 行内联构建）与 `ChatStreamServiceImpl`
（流式链路，原 `buildConversationContext`）：

```java
String summary = conversationContextService.getConversationSummaryIfPresent(conversationId);
String conversationContext = (summary == null || summary.isBlank())
        ? ""
        : "【更早的对话摘要】\n" + summary;
```

顺带删掉了 `ChatStreamServiceImpl` 里因此不再使用的 `import java.util.List`。

**改动 3：Python 读取条数 10 → 5**

`knowledge_qa_agent.py` 读记忆处：

```python
{"conversation_id": conversation_id, "limit": 5}
```

**改动 4：加对比日志**

```python
logger.info(f"[KnowledgeQAAgent] prompt_context_len={len(full_context)} "
            f"(java_summary={len(context)}, redis_history={len(conversation_history)})")
```

## 五、阶段 2（P1）：让 `user_memory` 真正可用（Step 1-3 ✅ 已完成 2026-11-14）

### 5.1 Step 1：建表 ✅

已加入 `sql/init.sql` 末尾，用 `CREATE TABLE IF NOT EXISTS` 而非 `DROP + CREATE`，
避免重新导入脚本时清空已积累的记忆数据（其余表保持 dump 原样）：

```sql
CREATE TABLE IF NOT EXISTS `user_memory` (
  `id` bigint NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `user_id` varchar(64) NOT NULL COMMENT '用户ID',
  `memory_key` varchar(64) NOT NULL COMMENT '记忆键, 如 preference.answer_style',
  `memory_value` text COMMENT '记忆值(JSON)',
  `source` varchar(32) DEFAULT 'agent' COMMENT '来源: explicit/inferred/agent',
  `confidence` double DEFAULT '1.0' COMMENT '置信度 0-1',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_key` (`user_id`, `memory_key`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户长期记忆';
```

`UserMemoryClient` 的 SQL 已经是 `ON DUPLICATE KEY UPDATE` 写法，与这个唯一键完全对应，建表后立即可用。
本地已执行并确认 8 个字段：`id / user_id / memory_key / memory_value / source / confidence / create_time / update_time`。

### 5.2 Step 2：只读接入 ✅

`knowledge_qa_agent.ask()` 在读完会话记忆之后、合并上下文之前读取：

```python
# 1.5 读取用户长期偏好（MySQL user_memory，缺失或异常时静默跳过）
user_memory_text = ""
if user_id:
    try:
        from core.mysql_client import user_memory_client
        memories = user_memory_client.get_user_memory(str(user_id)) or {}
        if memories:
            items = list(memories.items())[:10]      # 最多 10 条
            user_memory_text = json.dumps(dict(items), ensure_ascii=False)
            if len(user_memory_text) > 500:          # 最多 500 字符
                user_memory_text = user_memory_text[:500] + "..."
    except Exception as e:
        logger.warning(f"[KnowledgeQAAgent] Failed to load user memory: {e}")

if user_memory_text:
    block = f"[用户长期偏好] {user_memory_text}"
    full_context = f"{full_context}\n\n{block}" if full_context else block
```

两处防御是刻意加的：

- **条数与字符上限**：记忆条目不受控时会把 Prompt 撑爆
- **延迟 import + try/except**：MySQL 不可用时不能影响问答主流程

**这一步不改写入**，即使读到脏数据也只影响本次回答，可随时下线。

### 5.3 Step 3：写入接入 ✅（分两种来源）

| 来源 | 触发 | confidence | 风险 |
|---|---|---|---|
| **显式** | 用户说"记住我喜欢简洁的回答" | 1.0 | 低，但需要意图识别支持 |
| **推断** | 从对话里抽偏好 | 0.6-0.9（LLM 打分） | 高，会污染记忆 |

**最初只做正则，当天又升级为 LLM 抽取** —— 两版的差别与取舍都记在这里。

**v1（正则）**：只认显式表达，理由是抽取幻觉一旦写库，无法区分"用户真说过"和"模型编的"，
而且没有纠错入口时，错误记忆会长期生效，**比没有记忆更糟**。

**v2（预筛 + LLM，2026-11-14 追加）**：v1 上线后实测"换个说法就抽不到"过于常见
（"回答别太长""后面都给我表格"全部漏掉），靠加正则永远追不上用户的表达方式。
放开 LLM 抽取前，v1 阶段已把三个前提补齐，缺一个都不能放开：
- 记忆查看/删除接口（至少管理端有）✅
- `source` 与 `confidence` 落库，低置信度不参与 prompt ✅
- 抽取失败静默，不阻断主链路 ✅

**实际实现（2026-11-14）**：

1. 抽取链路：`_maybe_remember(user_id, question)` 把任务投递到专用线程池
   `_pref_executor`（2 并发），任务内先走 `extract_preferences()`（LLM），
   抽不到再走 `_rule_preferences()`（正则兜底）。抽取可能要走一次模型调用，
   **绝不能挂在请求线程上**。

   **1.1 LLM 抽取（`core/preference_extractor.py`）**

   | 环节 | 做法 | 为什么 |
   |---|---|---|
   | 预筛 `looks_like_preference()` | 信号词命中任一才继续 | 普通提问不花额外调用，"什么是并查集"零成本 |
   | 抽取 `extract_preferences()` | 一次调用，`temperature=0`、`max_tokens=300` | 抽取要确定性，不要创造力 |
   | 收敛 `_normalize()` | key 必须在白名单内、value 截断 30 字、`confidence < 0.5` 丢弃 | 模型自己发明字段会把 `user_memory` 写乱 |
   | 失败 | 任何异常 / 非法 JSON 一律返回 `[]` | 偏好抽取只是锦上添花，不能拖垮问答 |

   key 白名单与正则共用同一套：`answer_language / answer_format / nickname / preference`，
   两条路径写的是同一条记录（`uk_user_key` upsert 覆盖）。LLM 结果固定 `source=inferred`，
   置信度由模型打分；正则命中仍是 `explicit / 1.0` —— 显式指令不该被模型打分稀释。

   预筛词表按四类维护：

   | 类别 | 词 |
   |---|---|
   | 时间指向 | 以后 / 今后 / 往后 / 后面 / 之后 / 接下来 / 从现在开始 |
   | 指令口吻 | 统一 / 记住 / 请用 / 不要用 / 别用 / 别再 / 一律 / 始终 / 都要 |
   | 偏好自述 | 我喜欢 / 我习惯 / 我偏好 / 更喜欢 |
   | 称呼 | 叫我 / 称呼我 |

   **这里刻意放宽**：漏检的表现是"用户说了偏好但没记住"，比多花一次调用更难察觉。
   "后面都给我表格"就是因为原先只覆盖"以后/今后/统一"而被漏掉的。

   **1.2 正则兜底（`knowledge_qa_agent._PREF_RULES`）**

   4 元组 `(memory_key, 正则, source, confidence)`：

   | memory_key | 触发示例 | source | confidence |
   |---|---|---|---|
   | `answer_format` | 以后请用表格格式回答 | explicit | 1.0 |
   | `answer_language` | 以后请用中文回答 | explicit | 1.0 |
   | `nickname` | 请叫我老王 | inferred | 0.9 |
   | `preference` | 我一直喜欢简洁的回答 | inferred | 0.8 |

   命中后值以 `{"value": ..., "quote": 用户原话}` 落库；`quote` 只用于排查，不进 Prompt。

2. 接入点两处：同步链路 `ask()`（L1/L2 返回前）与流式链路 `ask_stream()`
   （流发完、忠实度评判派发之后）。之所以两处都挂，是因为聊天页走的是流式链路。

3. 读侧阈值：`USER_MEMORY_MIN_CONFIDENCE = 0.6`，`get_user_memory(user_id, min_confidence=0.6)`
   在 SQL 层过滤，低于阈值的记忆根本不会被注入 Prompt。

4. 管理接口（`api/memory_routes.py`，前缀 `/api`）：

   | 接口 | 说明 |
   |---|---|
   | `GET /api/memory/{user_id}` | 查看记忆，`min_confidence` 默认 0（管理端看全部） |
   | `DELETE /api/memory/{user_id}/{memory_key}` | 删除单条，不存在返回 404 |
   | `DELETE /api/memory/{user_id}` | 清空该用户全部记忆 |

   **鉴权**：复用 Java 侧签发的 JWT（HS256，`core/auth.py` 手写校验，不引 PyJWT）。
   `Authorization: Bearer <token>` 缺失/验签失败/过期 → 401；管理员（`role=ADMIN`）
   可操作任意 `user_id`，普通用户只能操作自己的 → 越权 403。
   Python 侧读 `JWT_SECRET` 环境变量，未配置时回退到与 Java `application.yml`
   相同的默认值并打 warning —— 生产环境必须两端配同一把密钥。

   关于为什么不校验 `sub`：Java 把用户 ID 放在 `userId` claim 里，`sub` 是用户名，
   所以授权判断只看 `userId`。

## 六、阶段 2.5（P3 + P4）：摘要架构收敛（rolling summary）

> 业界标准做法是 **rolling summary（滚动摘要）**：早期历史压成摘要、最近 N 轮保留原文、两者拼进 Prompt。
> 本项目「摘要 + 最近 5 条原文」的分工已经对了（阶段 1），但这套摘要本身的**生成与存储完全不符合标准**。

### 6.1 四条硬标准 vs 现状

| # | 标准 | 改造前 | 现状（2026-11-14 第 3 步完成后） |
|---|---|---|---|
| 1 | **事实源唯一**：持久化存摘要，Redis 只做缓存 | MySQL 关键词桩 + Redis LLM 摘要，互不相通 | ✅ MySQL 唯一事实源，`conv:summary:{id}` 只是缓存 |
| 2 | **生成器唯一**：同一 prompt、同一模型 | Java 关键词提取 + Python LLM，两份都不靠谱 | ✅ 唯一生成器是 `/api/internal/summarize`，关键词桩仅作兜底 |
| 3 | **可增量**：记录摘要覆盖到哪条消息 | 无游标，每次全量扫消息表 | ✅ `summary_msg_id` 游标 + `id > cursor` 增量 |
| 4 | **异步 + 可抑制**：不阻塞写消息、不重复触发 | 同步执行在 `@Transactional` 内 | ✅ afterCommit 触发 + 独立线程池 + CAS 抢占 |

现状证据：

```
  37~56 字符 5 条 | 139~264 字符 4 条
  1089 / 1265 字符 各 1 条                     ← 另一个极端：整句噪声
```

同步阻塞证据：

```126:127:src/main/java/com/demo/aiknowledge/service/impl/ConversationContextServiceImpl.java
    @Transactional
    public void updateConversationContext(Long conversationId, Long userId, Message newMessage) {
```

方法内部 `shouldGenerateSummary()`（全量查消息）+ `generateConversationSummary()`（全量查消息 + 写库）都在
这个事务里，而它由 `ChatPersistenceServiceImpl.saveUserMessage()`（同样是 `@Transactional`）调用 ——
每来一条消息全量扫一次 `message` 表，每 5 条再扫一次并写库，事务与行锁时间被拉长。

### 6.2 目标架构

```
写入路径
  消息落库（事务已提交）
     │ 触发条件：新增消息数 >= 5  或  估算 token > 2000
     ▼
  CAS 抢占：UPDATE conversation_context
           SET summary_status = 'generating', summary_update_time = NOW()
           WHERE conversation_id = ? AND (summary_status <> 'generating' OR summary_status IS NULL
                                         OR update_time < NOW() - INTERVAL 10 MINUTE)
     │ 影响行数 = 1 才继续（并发抑制：同一会话同时只跑一个任务）
     ▼
  summaryTaskExecutor.execute()   ← 独立线程池，不占 SSE 转发线程
     │ 取 id > summary_msg_id 的消息（增量，不全量，LIMIT 200）
     ▼
  POST /api/internal/summarize    ← Java 调 Python（summaryRestTemplate，读超时 10s）
     │ Header: X-Internal-Token
     │ Body: { conversation_id, old_summary, messages[] }
     ▼
  Python: LLM 合并摘要（old_summary + 增量消息）
     │
     ├─ 成功 → UPDATE summary / summary_msg_id / version+1 / status='ready'
     │         DEL Redis conv:summary:{id}
     └─ 失败 → 关键词桩兜底写入 + 推进游标 + status='failed'
               （failed 表示"这份是降级产物"，不是"没生成"）

读取路径
  getConversationSummaryIfPresent()
     │ 读 Redis conv:summary:{id}（TTL 1h）
     │   └─ miss → 查 MySQL summary → 回填 Redis
     │        └─ MySQL 也没有 → 用关键词桩同步补一份（毫秒级，填平异步空窗）
     ▼
  "【更早的对话摘要】" + Python 侧最近 5 条原文
```

关键点：**Redis 从这里开始只是缓存**。删掉它，系统仍然正确，只是多一次 MySQL 查询。

### 6.5 分三步实施（每步可独立上线、独立回滚）

**第 1 步：数据与读取（无行为变化）✅ 2026-11-14**
- 执行 §6.3 的 DDL：`sql/init.sql` 建表语句已加 4 列；存量库执行
  `sql/migration_summary_v2.5.sql`（本地库已执行并确认字段）
- 读取收敛的落点是 **`ConversationContextServiceImpl.getConversationSummaryIfPresent()`**，
  不是 `buildConversationContext()` —— 后者是 `ChatStreamServiceImpl` / `ChatServiceImpl`
  里的私有方法，两处都调这个 service 方法，改一处即覆盖两条链路
- 实现细节：直连 `StringRedisTemplate`（摘要就是一段纯文本），**不走 CacheService**
  —— 走那边会被套上 `conv:ctx:` 前缀并用 Jackson 序列化，读出来必然对不上
- **key 必须自成命名空间**：用 `conv:summary:{id}`，不复用 Python 的 `conversation:{id}:summary`。
  后者写的是 LLM 压缩摘要，且 `memory_read` 命中后直接使用、不再压缩；两边混用会让 Python
  把这里的关键词桩当 LLM 摘要直接注入 Prompt —— 静默的语义污染，查日志都看不出来
- TTL 取 3600 与 Python 侧一致，避免两边过期时间不一致导致命中率抖动
- 同时把 `getConversationSummary()`（会触发现场生成的那个）也接到同一读取路径，
  避免同一份摘要有两个来源
- 验证：本地 Redis 现有只有 `conversation:{id}:messages`，无摘要 key，
  故读取仍回源 MySQL，**摘要来源与改造前一致**；编译通过（`mvn -o compile`）

**第 2 步：异步生成 + 并发抑制 ✅ 2026-11-14**
- 事务提交后触发：`updateConversationContext()` 里注册 `TransactionSynchronization.afterCommit`
  （没有活动事务时直接触发），取代原先事务内的 `shouldGenerateSummary()` + `generateConversationSummary()`
- 触发条件：`SELECT COUNT(*) WHERE conversation_id=? AND id > summary_msg_id` ≥ 5。
  旧实现是 `messages.size() % 5 == 0`，每次都要全量扫表；新实现只做一次 count
- CAS 抢占 + 状态机 `none/generating/ready/failed`：
  ```sql
  UPDATE conversation_context
     SET summary_status='generating', summary_update_time=NOW()
  WHERE conversation_id=?
    AND (summary_status <> 'generating' OR summary_status IS NULL
         OR update_time < NOW() - INTERVAL 10 MINUTE)
  ```
  影响行数 = 1 才 `taskExecutor.execute(...)`，否则说明已有任务在跑
- 任务本体 `runSummaryTask()`：只取 `id > summary_msg_id` 的消息（`ORDER BY id ASC LIMIT 200`），
  成功后写 `summary / summary_msg_id / version+1 / status='ready' / summary_update_time`，
  再删 Redis 摘要缓存；失败只把 status 记 `failed`，**保留旧摘要**
- 生成器仍是 Java 关键词桩，抽成 `buildKeywordSummary(oldSummary, messages)`：
  **增量场景必须把旧摘要带上**（保留尾部 800 字，总长上限 2000），否则每轮只覆盖最近一批消息，
  早期内容整段丢失
- 五个防坑点（都是实测/复查才发现，不是设计时想到的）：
  1. **MySQL 同值更新返回 0 行**：卡死恢复时 status 本来就是 `generating`，只改 status 会被
     当成"没抢到"，必须顺带刷新一个时间列（`summary_update_time=NOW()`）才有实际变化
  2. 线程池拒绝执行时把 status 记 `failed` —— 否则该会话永久卡在 `generating`；
     只在「已抢到锁」时才回写，否则会把别人正在跑的 `generating` 覆盖掉
  3. 上下文行原本要到「每 10 条消息」保存长期记忆时才创建，这里补了懒创建，
     否则游标无处存放，摘要永远等不到第一次生成
  4. `generating` 超过 10 分钟视为任务已死（进程重启/线程丢失），允许被重新抢占；
     判据用 `update_time`（每次 UPDATE 自动刷新），已验证抢占后确实会刷新
  5. **`afterCommit` 里不能直接做查询/更新**：该阶段事务连接仍绑定在当前线程，MyBatis 会
     复用那条连接，写进去不提交、行锁也不释放，表现为状态停在 `generating` 而任务线程等锁
     直到超时。正确做法是 afterCommit 只负责 `taskExecutor.execute(...)`，
     把查询与 CAS 都放进任务线程（这个坑由集成测试偶发失败暴露，单跑复现不了）
- 顺带修掉一处隐患：`saveLongTermMemory()` 拿的是旧快照再 `updateById()`，会把摘要任务维护的
  `summary_msg_id / version / status / summary_update_time` 写回查询时的旧值（等于回滚游标）。
  现在保存前把这四个字段置空，交给 `updateById` 忽略 null 的默认行为
- 可观测性：触发阶段失败时除了 `log.warn`（带堆栈）还会把 `summary_status` 记 `failed`。
  "某个会话的摘要停在很早的位置"这件事在数据上就能查到，不必依赖翻日志 ——
  这正是排查这类静默降级最费劲的地方
- 实测（本地 MySQL 直接跑 CAS 语句）：`none`/`ready`/`failed`/`NULL` → 各 1 行；
  `generating` 且刚抢占 → 0 行；`generating` 但已卡死 20 分钟 → 1 行且 `update_time` 刷新
- 自动化测试（`src/test/java/.../service/impl/`）：
  - `ConversationContextSummaryTest`（5 项，Mockito）：阈值判断、CAS 成功/失败、线程池拒绝回滚、
    上下文行懒创建。**注意**：`LambdaQueryWrapper` 在没有 MyBatis 上下文时会抛
    "can not find lambda cache"，且异常被 catch 吞掉，表现为"方法什么都没做"，
    所以 `@BeforeAll` 里必须手工 `TableInfoHelper.initTableInfo(...)`
  - `SummaryTaskIntegrationTest`（5 项，`@SpringBootTest` 真连 MySQL/Redis）：首次生成 +

- **待第 3 步处理**：目前复用 `applicationTaskExecutor`（SSE 转发也用它）。关键词桩很轻，
  占不满线程池；但第 3 步换成 LLM 调用（8s 超时）后必须换独立线程池，否则会挤占流式响应

|---|---|
| 摘要任务失败导致摘要长期不更新 | `status='failed'` 可被下次触发覆盖；同时保留旧摘要，不至于"没摘要" |
| 异步线程池被打满 | 摘要任务用独立线程池或低优先级队列，与流式响应隔离 |
| LLM 生成摘要不稳定 | 超时 + 失败降级到规则摘要；规则摘要代码保留不删 |
| 增量摘要丢失上下文 | 每次把 `old_summary` 一并传入，让模型做"合并"而非"重写" |
| 回滚 | 三步各自独立提交；第 3 步出问题可回退到关键词桩，前两步仍然有效 |

**工作量**：第 1 步 0.5 天 / 第 2 步 0.5 天 / 第 3 步 1 天，合计约 2 天。

### 6.8 明确不做的

|---|---|

**关于"MySQL 挂掉"这条的修正结论**（原表述过于笼统，实测后才分清）：

| 场景 | 结果 | 结论 |
|---|---|---|
| 只有 Python 连不上 MySQL（`MYSQL_PORT=3999`） | 问答正常返回 99 字，日志 `[UserMemory] Failed to load user memory: Can't connect to ...:3999` | ✅ 记忆模块的降级是对的 |

只能拒绝。也就是说**整库不可用时整个服务不可用**，跟记忆功能无关；
记忆模块自己能做到的降级（读写失败静默）已经做到了。

## 十二、工程化改动与欠账（2026-11-14）

不在原计划内，但会反复咬人的两项，已处理。

### 12.1 命令行输出编码统一

现象：终端是 UTF-8（chcp 65001），Java/Python 子进程却按 GBK(cp936) 写 stdout，
中文被按 UTF-8 解码成一片 `��`。服务日志一直是正常的（`start-all.ps1` 早已加
`-Dstdout.encoding=UTF-8` / `PYTHONUTF8=1`），漏的是 `mvn test` 与 `pytest` 两条命令行通道。

| 缺口 | 修法 |
|---|---|
| mvn 自身 JVM | `.mvn/jvm.config` 指定 UTF-8 |
| surefire fork 的测试 JVM（**不继承** mvn 的 `-D` 参数） | `pom.xml` 的 surefire `argLine` |
| pytest 把中文参数转义成 `\u4ee5\u540e` | `pytest.ini` 关闭 escaping |
| Python 进程输出编码 | 用户级 `PYTHONUTF8=1`（PEP 540） |

两个被否掉的方案（都实测无效，记下来免得再试）：

- `conftest.py` 里 `sys.stdout.reconfigure()`：pytest 在导入 conftest **之前**就建好 capture 流
  并固化了当时的编码，改表面属性无效（`sys.stdout.encoding` 显示 utf-8，写出的仍是 GBK）
- `sitecustomize.py`：该钩子被 IDE shim 占用，项目内的同名文件永远不会被加载，
  `sitecustomize.__file__` 指向的是别的路径

### 12.2 CI 真跑集成测试

- 集成测试加 `@RequiresLocalInfra`：MySQL/Redis 不可达时整类跳过，不再以 Hikari 超时形式变红
- `.github/workflows/ci.yml` 的 `java-test` 起 `mysql:8.0` + `redis:7`，导完 schema 再跑全量测试
- **`sql/init.sql` 全量导入会失败**：`admin_message` 有 9 列，导出的 INSERT 只给 7 个值
  （缺 `feedback_type` / `feedback_time`），报 1136 Column count doesn't match。
  CI 因此只导 schema（`grep -v '^INSERT INTO'`），集成测试自造数据、不依赖种子数据

### 12.4 端到端回归揪出的三个断链（2026-11-14）

pytest 111 项全绿，但真实链路是断的 —— 因为这三个 bug 全在"参数透传"和"事件契约"上，
单测直接调 agent，绕过了 HTTP 层，所以测不出来。

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 说了"后面都给我表格"，`user_memory` 始终为空 | `api/routes.py` 的流式链路调 `route_stream` 时没传 `conversation_id` / `user_id`，两者取默认值 `None` | 补齐透传 |
| 2 | 补了透传仍不生效，回答"像失忆" | `ask_stream` 里压根没有读记忆的代码，只用了 Java 摘要；`_build_full_context` 只存在于同步链路 `ask()` | 抽成共用方法，两条链路都调 |
| 3 | 复杂问题（L3）回答一片空白，刷新后彻底消失 | L3 只发 `{type:"answer"}`，而 Java 落库 switch 与前端 `Chat.jsx` 的 switch 都只认 `token` / `end` | 改为 token + sources + end，与 L1/L2 同构 |

顺带修掉的一致性缺口：

- 同步链路也漏传 `user_id` —— 写偏好对着 `None` 静默跳过
- L3 不注入用户偏好（`reason()` 没有 `user_id` 参数）→ 新增参数并复用 `core/preference_context`

两个量化证据：

```
修复前: 说偏好后 user_memory 0 条; 管理端轨迹 5 步(无"记忆读取"); L3 回答 0 字
修复后: user_memory 写入 answer_format=表格(0.95); 轨迹 6 步(含"记忆读取"); L3 回答 2082 字且含表格
```

教训：**跨进程的参数透传与事件契约，只能靠端到端验证**。这个项目已经因为
`conversation_id` 断链"失忆"过一次，这次是同一类问题的三个新变体 —— 都是在
"看起来能跑"的状态下静默失效。
