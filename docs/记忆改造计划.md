## 一、现状全景（代码核实，非推测）

### 1.1 两条轨并存

```
用户提问
  │
  ├─【Java 轨】事实存档，跨会话永久
  │    ChatServiceImpl / ChatStreamServiceImpl
  │      → conversationContextService.getConversationContext(id, 10)   ← 从 MySQL 取最近 10 条
  │      → 拼成 "user: xxx\nassistant: yyy"
  │      → AiServiceImpl:311  requestBody.put("context", ...)
  │
  │    消息落库时（ChatPersistenceServiceImpl:41/59 → updateConversationContext）
  │      → 滑动窗口 + Caffeine/Redis 缓存（key=conv:ctx:{id}，TTL 1800s）
  │      → 每 5 条：generateConversationSummary()   【关键词提取，不调 LLM】
  │      → 每 10 条：saveLongTermMemory()           【真写 conversation_context 表】
  │
  └─【Python 轨】模型上下文，24 小时
       knowledge_qa_agent.ask()
         → conversation_memory_read(limit=10)        ← 从 Redis 取最近 10 条
         → _format_history()  拼成 "用户: xxx\nAI: yyy"
         → full_context = f"{context}\n\n{conversation_history}"   ← ★ 与 Java 轨叠加
         → _ask_l1 / _ask_l2
         → conversation_memory_write() 写回
```

### 1.2 各组件真实状态

| 组件 | 状态 | 证据 |
|---|---|---|
| Java `getConversationContext()` | ✅ 在用 | `ChatServiceImpl:108`、`ChatStreamServiceImpl:216` |
| Java `updateConversationContext()` | ✅ 在用（每次落消息） | `ChatPersistenceServiceImpl:41/59` |
| Java `generateConversationSummary()` | ✅ 在用（每 5 条），**不调 LLM** | `ConversationContextServiceImpl:187` 注释自承"简化版" |
| Java `saveLongTermMemory()` | ✅ 在用（每 10 条），写 `conversation_context` | `ConversationContextServiceImpl:253` |
| Java `findSimilarConversations()` | ❌ **零调用**，关键词匹配 | 仅定义处命中 |
| Python `conversation_memory_read/write` | ✅ 3 个 Agent 在用（问答/推理/闲聊） | `knowledge_qa_agent` `reasoning_agent` `chitchat_agent` |
| Python `UserMemoryClient` | ❌ **零调用**，且 `user_memory` 表不存在 | `core/mysql_client.py:210-275`；`init.sql` 无该表 |
| `conversation_context.embedding` | ⚠️ 字段存在，从未写入 | 表结构有，代码无赋值 |

### 1.3 关键结论：重复从第一天就存在，修好透传后才显形

```
61ebd6d（初始提交）
  ├─ Java 已把 getConversationContext(10) 拼进 context
  └─ Python 已写 full_context = context + conversation_history
      → 双轨从第一天成立

踩坑笔记 §2「会话记忆链断裂」
  conversation_id 未跨服务透传
  → Java getConversationContext(null) 返回空 → context = ""
  → Python 读不到 Redis → conversation_history = ""
  → 两路都空 → 表现为"AI 失忆"
  修复：Java 请求体加 conversation_id（+ user_id）

修复之后
  → Java 那路有 10 条了
  → Python 那路也有 10 条了
  → ★ 重复第一次显形
```

**这不是"修坏了"**，而是修复让一个从未被定义的问题暴露出来：**从来没有人规定"上下文由谁负责"**。
当时的验证方式（看 Python 日志 `Loaded N messages`）只覆盖了一路，看不出另一路也在塞。

## 二、问题清单（按严重度）

| # | 问题 | 影响 | 位置 |
|---|---|---|---|
| **P0** | 双轨上下文重复注入 | 同一批对话在 prompt 里出现两次：Token 翻倍、可能干扰生成、引用错乱 | `knowledge_qa_agent.py:81` |
| **P1** | `user_memory` 表与 `UserMemoryClient` 是死代码 | 无法记住用户偏好；代码留着会误导后来者以为"已有长期记忆" | `core/mysql_client.py:210` |
| **P2** | `findSimilarConversations()` 零调用 + 关键词匹配 | "跨会话记忆"名存实亡 | `ConversationContextServiceImpl` |
| **P3** | 摘要是关键词提取，非 LLM | `summary` 质量低，`importance_score` 也不准 | `ConversationContextServiceImpl:187` |
| **P4** | `conversation_context.embedding` 从未写入 | 字段闲置，若做 P2 需先补 | 表结构 |

## 三、改造原则

1. **单一职责**：Java 管"事实存档"（审计、管理端展示），Python 管"喂模型的上下文"。两边的数据可以重叠，**但拼进同一个 prompt 的内容不能重叠**。
2. **先减法后加法**：P0 是纯减法，改完立刻能测出效果；P1 之后都是给模型加信息，加错了会降低回答质量。
3. **每阶段可独立上线、可独立回滚**。
4. **不引入新中间件**：复用现有 MySQL + Redis；只有 P2 需要向量检索时才考虑 Milvus。

## 四、阶段 1（P0）：消除重复注入 ✅ 已完成（2026-11-14）

**目标**：一次 prompt 里，历史对话只出现一次。

**实施结果**：改动 5 个文件，实测 prompt 上下文长度从约 4 万字符降到 9307 字符（降幅约 77%），
且摘要是压缩表示、不与最近几轮原文重复。

### 4.1 最终方案：Java 只传摘要，Python 传最近 5 条原文

| 侧 | 传什么 | 为什么 |
|---|---|---|
| Java | `conversation_context.summary`（存在时，前缀"【更早的对话摘要】"）；不存在则传空串 | 摘要覆盖更早的历史，MySQL 永久不过期 |
| Python | 最近 5 条原文 | 保证衔接自然，且保留 LLM 压缩能力 |

> **与原方案的差异（实施时调整）**：原计划是"摘要 + 最近 2 条原文"，实施时改为**只传摘要**。
> 原因：那 2 条原文必然包含在 Python 读取的最近 5 条里，仍会重复。改成"摘要 + 5 条原文"后，
> 两者形态不同（压缩表示 vs 原文），边界清晰。

**为什么不选其他方案**：

| 方案 | 否决理由 |
|---|---|
| 删掉 Java 的 context | Redis 24h 过期后历史全丢，长对话断裂 |
| 删掉 Python 的 Redis 读取 | 失去 LLM 压缩能力，Java 的摘要是关键词提取，质量差 |
| 两边都保留但只取较短的一边 | 逻辑上等价于选一个，不如显式分工 |

### 4.2 实际改动（已完成，共 5 个文件）

**改动 1：新增只读摘要方法**

`ConversationContextService` 接口 + `ConversationContextServiceImpl` 实现各加一个：

```java
String getConversationSummaryIfPresent(Long conversationId);
```

为什么不直接用已有的 `getConversationSummary()`：它在摘要缺失时会**现场重新生成并写库**
（全量扫消息表 + `updateById`），每次提问都调用代价太大。新方法只 `selectOne` 一次，
缺失返回 `null`，异常也返回 `null`——摘要只是上下文补充，不能影响问答主流程。

**改动 2：Java 两处构建上下文改为只传摘要**

`ChatServiceImpl`（同步链路，原 108 行内联构建）与 `ChatStreamServiceImpl`
（流式链路，原 `buildConversationContext`）：

```java
String summary = conversationContextService.getConversationSummaryIfPresent(conversationId);
String conversationContext = (summary == null || summary.isBlank())
        ? ""
        : "【更早的对话摘要】\n" + summary;
```

顺带删掉了 `ChatStreamServiceImpl` 里因此不再使用的 `import java.util.List`。

**改动 3：Python 读取条数 10 → 5**

`knowledge_qa_agent.py` 读记忆处：

```python
{"conversation_id": conversation_id, "limit": 5}
```

**改动 4：加对比日志**

```python
logger.info(f"[KnowledgeQAAgent] prompt_context_len={len(full_context)} "
            f"(java_summary={len(context)}, redis_history={len(conversation_history)})")
```

### 4.3 验收（实测数据）

| 轮次 | 记忆消息数 | 日志 |
|---|---|---|
| 第 1 轮 | 0 | `prompt_context_len=0 (java_summary=0, redis_history=0)` |
| 第 2 轮 | 2 | `Loaded 2 messages` → `prompt_context_len=1495` |
| 第 3 轮 | 4 | `Loaded 4 messages` → `prompt_context_len=4022` |
| 第 4 轮 | 5 | `Loaded 5 messages`（封顶）|
| 第 5 轮 | 5 | `Loaded 5 messages`（封顶）|
| 带摘要的请求 | 5 | `prompt_context_len=9307 (java_summary=65, redis_history=9240)` |

结论：
- `limit=5` 封顶生效（原 10 条）
- 摘要与最近几轮原文并存，形态不同、不重复
- 上下文总量较改造前（Java 10 条原文 + Python 10 条原文）下降约 **77%**

回归：

```
pytest 54 passed            ← 无新增失败
mvn compile / package 通过   ← 5 个 Java 文件改动全部编译通过
Java 服务重启后接口正常响应    ← /api/auth/login 返回业务码 4001（密码错误），说明服务通
```

### 4.4 风险与回滚

| 风险 | 应对 |
|---|---|
| 摘要为空（新会话前 5 条内）→ Java 只传 2 条 | 正常：短会话本来就靠 Python 那 5 条 |
| `getConversationSummary` 返回 null | 已做 null 判断，退化为"只传 2 条" |
| 回滚 | 只改 2 个文件，`git revert` 单个提交即可 |

**工作量**：半天（含验证）。

## 五、阶段 2（P1）：让 `user_memory` 真正可用

### 5.1 Step 1：建表

```sql
CREATE TABLE `user_memory` (
  `id` bigint NOT NULL AUTO_INCREMENT,
  `user_id` varchar(36) NOT NULL COMMENT '用户ID',
  `memory_key` varchar(64) NOT NULL COMMENT '记忆键, 如 preference.answer_style',
  `memory_value` text COMMENT 'JSON 值',
  `source` varchar(32) DEFAULT 'agent' COMMENT 'explicit / inferred / agent',
  `confidence` double DEFAULT '1.0' COMMENT '置信度 0-1',
  `create_time` datetime DEFAULT CURRENT_TIMESTAMP,
  `update_time` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_key` (`user_id`, `memory_key`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户长期记忆';
```

`UserMemoryClient` 的 SQL 已经是 `ON DUPLICATE KEY UPDATE` 写法，与这个唯一键完全对应，建表后立即可用。

### 5.2 Step 2：只读接入（低风险，先单独上线）

`knowledge_qa_agent.ask()` 读完会话记忆之后：

```python
user_memory = {}
if user_id:
    try:
        user_memory = user_memory_client.get_user_memory(user_id) or {}
    except Exception as e:
        logger.warning(f"[KnowledgeQAAgent] load user memory failed: {e}")

if user_memory:
    mem_text = json.dumps(user_memory, ensure_ascii=False)
    full_context = f"{full_context}\n\n[用户长期偏好] {mem_text}" if full_context else f"[用户长期偏好] {mem_text}"
```

**这一步不改写入**，即使读到脏数据也只影响本次回答，可随时下线。

### 5.3 Step 3：写入接入（分两种来源）

| 来源 | 触发 | confidence | 风险 |
|---|---|---|---|
| **显式** | 用户说"记住我喜欢简洁的回答" | 1.0 | 低，但需要意图识别支持 |
| **推断** | 从对话里抽偏好 | 0.6-0.9（LLM 打分） | 高，会污染记忆 |

**第一版建议只做显式 + 极简规则推断**（例如"我是做 Java 的"→ `occupation=Java`），
不做开放式 LLM 抽取。理由：抽取幻觉一旦写库，无法区分"用户真说过"和"模型编的"，
而且没有纠错入口时，错误记忆会长期生效，**比没有记忆更糟**。

如果要做，必须同时提供：
- 记忆查看/删除接口（至少管理端有）
- `source` 与 `confidence` 落库，低置信度不参与 prompt
- 抽取失败静默，不阻断主链路

### 5.4 验收

```
1. 单元测试：写入 → 读取 → prompt 里出现
2. 端到端：说一句"我喜欢简洁回答" → 下个会话提问 → 回答明显变短
3. 未登录（user_id 为空）→ 不报错，行为与改造前一致
4. pytest 全绿
```

**工作量**：建表 10 分钟；只读接入半天；显式写入 1 天；规则推断 +1 天。

## 六、阶段 3（P2）：跨会话检索

`findSimilarConversations()` 要能用，前提是**按 user_id 过滤的向量检索**。

| 方案 | 可行性 | 说明 |
|---|---|---|
| FAISS + 后过滤 | ⚠️ 能跑但低效 | FAISS 不支持元数据过滤，只能全量召回再筛 |
| Milvus + filter | ✅ 推荐 | `USE_MILVUS=true` 后 `vector_store.search(filter_dict=...)` 已支持 |
| MySQL 关键词 + 重要性排序 | ✅ 最简单 | 就是现在的实现，先把功能接上 |

**建议路线**：
1. 先把 `findSimilarConversations` **接进链路**（哪怕仍是关键词匹配），让"跨会话记忆"可用；
2. 补 `conversation_context.embedding` 写入（P4）；
3. 用户量/数据量上来后再切 Milvus 过滤。

**工作量**：接链路 1 天；补 embedding 1 天；切 Milvus 1-2 天。

## 八、明确不做的事

| 不做 | 原因 |
|---|---|
| 引入专门的记忆框架（Mem0 / Zep 等） | 当前规模用 MySQL + Redis 足够，引入后调试成本高于收益 |
| 用 LLM 重写 Java 侧的摘要 | 阶段 1 之后摘要只作兜底，投入产出比低；且会给 Java 链路增加 LLM 依赖 |
| 让 Python 直接读 MySQL | 破坏服务边界（Java 管持久化），且连接池管理成本翻倍 |
| 把 Redis 会话记忆改到 MySQL | Redis 的 TTL 语义正是我们要的，改过去要自己实现过期 |
